# Telegram — планирование сообщений на сутки

**READY — локальная демонстрация, без отправок.**

## ORIGINAL
Desktop/РАБОТА/Приложения/скрипт рассылка: Python, Playwright, Typer, Pydantic, Docker/cron. README описывает 1 немедленное сообщение и 23 отложенных, по одному через час, для чатов в выбранных папках. Это одноразовый проход; регулярный запуск обеспечивает cron. Все 12 отобранных исходных файлов побайтно совпали с папкой «скрипт рассфлка заказчику» — она учтена как копия, не потерянный самостоятельный проект.

## VERIFIED
Из исходного forward_cli.py через AST извлечена без изменения функция process_folder. Выполнены шесть сценариев: обычный, dry-run, частичный сбой, повтор peer_id, отсутствующая и пустая папка. На двух синтетических группах нормальный проход даёт 48 mock-операций; ошибка на седьмом часу — 46, повтор группы не создаёт вторую очередь. Dry-run не вызывает отправку. Отчёт api-qa.json содержит реальные результаты функции с заглушками, а не заранее нарисованную статистику.

## PORTFOLIO POLISH
Новая панель с редактором, суточным расписанием, деталями групп, предупреждениями, JSON-выгрузкой и журналом. Оригинальный продукт был CLI/браузерной автоматизацией; новый интерфейс не приписывается исходному релизу. Визуальные ориентиры: [Buffer calendar](https://support.buffer.com/en-us/articles/how-to-use-buffers-calendar-feature-FSSKbH32DN), [Typefully scheduling](https://support.typefully.com/en/articles/9210135-scheduling-and-calendar), [Later calendar](https://later.com/social-media-content-calendar/). Использованы компактные временные слоты и разделение редактора/результата, без копирования чужого UI.

## DEMO / MOCK
FakePage, FakeNavigation, FakeForwarder и синтетические рабочие группы «Север» / «Лист». Время зафиксировано для повторяемости. Извлечение названия чата заменено mock; save_chat_info направлен в память, а не в клиентский журнал. TelegramAuth и run_forward_scenario не вызываются. auth.json, реальные конфигурации, сессии и sent_messages не читались. Отчёт скачивается из локального результата; никто не получает сообщений.

## Ограничения
Оригинальный stats.success означает завершённую обработку чата даже при частично неудачном планировании. Панель отдельно показывает фактические операции и предупреждения. Дедупликация ограничена переданным set текущего запуска; постоянная идемпотентность не доказана. В исходной функции количество отложенных сообщений жёстко равно 23. Работа Telegram Web selectors, авторизация и cron сейчас не проверены. Личная роль Никиты и публичные права требуют подтверждения.

## PLANNED
Production-обвязка панели, реальный транспорт, безопасный повтор частичного запуска и настройка произвольного расписания не реализовывались для кейса. Возможности исходного CLI не следует смешивать с новой визуализацией.

## QA и материалы
Все шесть режимов, JSON-выгрузка, история и валидация/ошибка соединения/повтор проверены на 390/768/1440. Два master около 38 секунд записаны с паузами для чтения, без изменения скорости. Оба экспорта просмотрены по кадрам; case QA 320/390/768/1440 проверяет пропорции видео и постеров.

## VISUAL BLOCKED — реальный Telegram UI

Найдено реальное видео Telegram Desktop, но в нём видны личные чаты и DevTools, а основной экран долго остаётся в загрузке. Публиковать запись нельзя; нужен новый обезличенный capture реального Telegram-сценария.

Подготовленные интерфейсы, тесты и видео сохранены как исследовательские материалы, но исключены из READY-витрины до появления проверяемого пользовательского Telegram-сценария.
